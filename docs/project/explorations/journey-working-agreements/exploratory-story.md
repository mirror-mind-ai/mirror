# Exploratory Story: Journey Working Agreements

## Source

- Journey: `mirror-ts-core`
- Durable Story: `a3f002c5`
- Origin mode: Explorer Mode
- Raw conversation included: no

## Original Question

How could a journey remember not only its identity and history, but the agreed way work
should happen inside it? The source package proposed a Journey Context Contract with
named task profiles, personas, compatible modes, required and optional references,
default behavior, explainable resolution, and conversational learning under explicit
confirmation.

## Product Attractor

A journey becomes an **environment of work**, not merely a container of context. A short
request such as “rewrite this passage” can select the journey's authoring profile,
persona, voice guide, and rubric. “Diagnose this chapter without rewriting” can select a
more specific editorial profile in the same journey. The user speaks about the work;
Mirror translates the request into the journey's working agreement.

## Tensions Surfaced

### Automatic resolution versus durable mutation

Profile resolution may occur on every relevant turn. Learning a durable rule may create
a proposal automatically, but only attributable user confirmation can activate a new
revision. Execution clarification and contract learning remain separate interactions.

### Journey coordination versus authority

A contract may select context and a lens. It cannot authorize implementation, commit,
push, release, deployment, purchase, publication, filesystem mutation, or another hard-
gated action. Builder, Explorer, Soul, safety, and explicit user authority remain above
journey-owned guidance.

### Product value versus migration timing

The source package was captured against `v0.31.9` and described a predominantly Python
implementation. Grounding against the live `mirror-ts-core` branch found that CV22 now
owns schema and migration custody in TS, while Mirror Mode orchestration, reception,
context composition, and live provider transfer remain moving boundaries. A Python-first
implementation would create immediate parity debt; absorbing the capability into
CV22.DS7.US4 would turn migration parity into a large product expansion.

### Useful foresight versus premature roadmap commitment

The delivery sequence is understandable enough to preserve, but not stable enough to
materialize as an active CV and story tree. File paths, migration numbers, provider
interfaces, runtime adapters, and CV22 dependencies will continue to move. Preserving a
provisional map is valuable; pretending it is an approved plan is not.

## Evolution Of The Exploration

1. The source package was understood as a general journey capability rather than a
   writing-specific default persona.
2. A provisional placement emerged: a separate **Journey Working Agreements**
   capability, likely CV23, instead of expansion inside CV22 parity work.
3. Live grounding identified CV22.DS7.US4 as the first relevant orchestration plateau,
   CV22.DS8 as the live-model dependency, and CV22.DS10 as the later web boundary.
4. A detailed seven-Delivery-Story sequence was designed, from contract authority to
   cross-runtime convergence and later web management.
5. The Navigator recognized that the work is too large for the current horizon.
6. The exploration changed from near-term delivery design to deliberate preservation:
   retain evidence and reasoning, add a Radar marker, define re-entry triggers, and
   avoid creating active roadmap work now.

## Current Story

Journey Working Agreements remains a strong future capability. It is deferred, not
rejected. The original ten-document package is preserved verbatim as historical source
evidence. The product synthesis and provisional delivery sequence are preserved
separately so future Builder work can distinguish durable product intent from stale
implementation assumptions.

Re-entry should happen only after the TS Mirror Mode seam is stable, live-provider
planning has a real interface, schema authority remains clear, and the Navigator chooses
the capability as current work. The future session must inspect the live repository and
create fresh delivery plans rather than executing this exploration mechanically.

## Current Summary

Preserve now; re-ground later; implement TS-native when the migration can support the
capability without duplicating authority.
