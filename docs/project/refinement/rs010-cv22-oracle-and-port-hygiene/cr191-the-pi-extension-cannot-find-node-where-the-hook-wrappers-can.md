# CR191 — The Pi extension cannot find Node where the hook wrappers can, and says nothing when it cannot

## Problem

Every Mirror command the Pi extension (`.pi/extensions/mirror-logger.ts`) runs is a
`node` process: the awaited ones through `pi.exec`, the maintenance and close work
through a detached `spawn`. The extension resolves `node` in two steps: `MIRROR_NODE`
when it names an existing path, else the bare name `node` on the PATH Pi inherited.
When neither resolves, nothing works and nothing says so.

Until PR #47 (merged 2026-11-02, Rodrigo Immaginario), the detached spawn had no
`'error'` listener, so a missing `node` was an uncaught exception and Pi exited:

```text
pi exiting due to uncaughtException:
Error: spawn node ENOENT
    at ChildProcess._handle.onexit (node:internal/child_process:316:19)
  spawnargs: [ '…/node_modules/mirror-mind/bin/mirror.js', 'conversation-logger', 'session-maintenance' ]
```

Seen on 2026-10-16: a Pi opened from a window whose PATH predated the Node install. The
same happens wherever `node` is not on the PATH a GUI-launched Pi inherited, which
`hookNodeFindings` in `ts/src/runtime/diagnose.ts` names as the usual case ("`node`
usually lives under nvm or Homebrew and is NOT on the PATH a GUI-launched runtime
inherits").

PR #47 made the failure non-fatal and made the extension honor `MIRROR_NODE`. What
remains is the gap between the extension and the rest of the runtime wiring:

1. **The extension does not look where the hook wrappers look.** A wrapper generated by
   `scripts/generate_hook_wrappers.sh` resolves Node as `$MIRROR_NODE` (when
   executable), then `command -v node`, then the Node beside the entry it runs, then
   `~/.nvm/current/bin/node`, `/opt/homebrew/bin/node`, `/usr/local/bin/node`. The
   extension stops after the first two. The Node beside the tree it ships in
   (`<prefix>/lib/node_modules/mirror-mind` → `<prefix>/bin/node`, the Node that installed
   the package) is the one the 2026-10-16 incident needed, and would have needed no
   configuration.
2. **`runtime diagnose` and the extension disagree about what "resolvable" means.**
   `hookNodeFindings` reports nothing when any of its candidates exists, so on a machine
   with `/opt/homebrew/bin/node` it says Node is fine while a GUI-launched Pi's extension
   fails. The one place a user is told to ask does not know about the one runtime that
   fails.
3. **The failure reaches no one.** Pi's `pi.exec` reports a spawn failure as exit 1 with
   the message in stderr; `runMirror` logs a WARN to `mirror-logger.log` and returns
   empty. The session opens with no welcome card, no status, no logging, no doorman, and
   no notice. The extension already has the pattern for this (the one-time
   `` Mirror: `mirror` is not on the PATH `` notice at `session_start`) and does not use
   it here. The wrappers write their failure to `<mirror home>/hooks.log`, which
   `hookFailureFindings` surfaces for seven days; the extension writes nowhere diagnose
   reads. This is the failure the wrapper generator's own comment was written against:
   "an unresolvable Node is RECORDED, never swallowed", because the user meets it weeks
   later as "Mirror stopped remembering".
4. **The log contradicts itself.** When the spawn fails, `child.pid` is `undefined`, and
   `runMirrorBackground` still logs
   `session-maintenance started in detached background process (unknown pid)` before the
   `failed to start` line.
5. **Smaller gaps from the review of PR #47** (engineer, devops-engineer,
   quality-assurance, security-engineer, 2026-11-01):
   - `nodeCommand()` accepts a directory or a non-executable file (`existsSync`), while
     the file's own `_mirrorOnPath` and the wrappers' `-x` check for an executable.
   - A `MIRROR_NODE` that names nothing falls through to the PATH silently.
   - A relative `MIRROR_NODE` resolves against whatever project Pi was opened in.
   - The fake `pi.exec` in `ts/test/pi/mirrorLoggerExtension.test.ts` drops its
     `command` argument, so nothing asserts the awaited execs receive the resolved Node.
   - The two new tests wait a fixed 200 ms for a next-tick event.
   - `REFERENCE.md`'s `MIRROR_NODE` row names "the hook wrappers and the plugin's MCP
     entry"; the Pi extension is not among the readers it lists.

## Expected Behavior

- The extension resolves Node in the wrappers' order: `MIRROR_NODE` when it is an
  executable file, the PATH, the Node beside the tree it ships in, then the candidates
  `HOOK_NODE_CANDIDATES` names. A test pins the extension's list to the core's, as
  `hooks.test.ts` pins the wrappers' (the two lists drifted once before, TS5 handoff
  finding N1).
- A Pi opened where no Node resolves stays up, says so once in the session, naming the
  fix (`MIRROR_NODE=/path/to/node`, Node 24 or later), and writes one line to
  `<mirror home>/hooks.log` in the wrappers' format, so `runtime diagnose` reports it as
  `hook_failures_recorded`.
- A `MIRROR_NODE` that is not an executable file is reported once per process, then the
  search continues.
- The log tells one story: a child that did not start is not logged as started.
- `runtime diagnose`'s `hook_node_unresolvable` and the extension agree: when diagnose
  finds no Node, neither does the extension, and when the extension finds one, diagnose
  reports nothing.
- `REFERENCE.md` and `docs/reference/configuration.md` name the Pi extension among
  `MIRROR_NODE`'s readers, and `docs/process/troubleshooting.md` names the Pi notice
  beside the hooks' `hooks.log` line.

## Impact

Medium. Before PR #47, a GUI-launched Pi crashed at startup, which is loud and was fixed
within the week. After it, the same Pi runs with Mirror absent: no conversation is
logged, no context is delivered, and the only evidence is a line in a file the user is
never pointed at. That is the silent failure the wrappers and `runtime diagnose` were
built to prevent for the other four runtimes, and Pi is the runtime the maintainer uses
daily.

- Every user whose Pi is launched from a GUI, or from a shell whose PATH predates nvm or
  Homebrew, meets it. `hookNodeFindings` calls this the usual case.
- `MIRROR_NODE` users are now affected on Pi too, since PR #47: a stale `MIRROR_NODE`
  (set for Claude's hooks months ago, pointing at an older Node) breaks Pi silently.
- The incident's own repair route is incomplete: `runtime diagnose` says nothing on the
  machine that fails, because a candidate exists that the extension never tries.

## Plan Or Decision

Captured, unassigned, 2026-11-02, at the Navigator's direction, after PR #47 was merged
as the first part of the fix.

Not planned. Decisions for Plan:

- **Search order and parity test.** Whether the extension duplicates the candidate list
  (it is a thin dispatcher and imports no core module, as it duplicates the homes-root
  names today) with a test that pins it to `HOOK_NODE_CANDIDATES`, or the core exposes
  the list another way.
- **The notice.** Once per session at `session_start`, as the `mirror`-not-on-PATH
  notice; and whether a failure later in the session (a `MIRROR_NODE` that moved) also
  speaks or only logs.
- **The `hooks.log` line.** Its hook label (`pi:session-start`, `pi:<label>`), written by
  the extension, in the format `hookFailureFindings` parses.
- **A Node too old.** The wrappers report a non-zero exit with the Node's version and
  "Mirror needs Node 24 or later". Whether the extension does the same from the detached
  child's `exit` event and the awaited exec's exit code.
- **Relative `MIRROR_NODE`.** Whether the extension requires an absolute path (a secure
  default the wrappers do not share) or the family does, as a separate CR.
- **Tests.** Replace the fixed waits with a poll on the log; capture the fake exec's
  command; add the directory, the missing path, and the search-order cases.
