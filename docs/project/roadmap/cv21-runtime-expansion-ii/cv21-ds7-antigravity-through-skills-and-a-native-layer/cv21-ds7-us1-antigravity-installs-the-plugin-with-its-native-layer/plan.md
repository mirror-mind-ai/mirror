# Plan — CV21.DS7.US1

## Objective

Make the shipped plugin installable on Antigravity with its native layer.
`agy plugin install` already takes the Claude plugin's 25 skills (DS12.TS3
static 3) but stages Claude's hooks file verbatim — unrunnable (static 4) —
and skips `mcpServers`. This story makes the package carry what agy *can*
run: an agy-schema hooks file, `mcp_config.json`, and `rules/AGENTS.md`,
generated by the same builder that owns the Claude surfaces, staged by the
same install command, printed by `mirror init`. The hooks file ships
schema-valid; TS2 and TS3 put injection and logging behavior into it.

**What the evidence pins and what it does not.** DS12.TS3 pinned the
mechanisms (SessionStart `injectSteps` → `systemMessage`, L1; `PreInvocation`
per model call, L2; `rules/AGENTS.md` and `mcp_config.json` as the plugin's
files, static 7) but the repository holds no byte-exact schema for agy's
hooks file, and two install behaviors are unmeasured: whether `agy plugin
install` stages a package-shipped agy-schema hooks file as-is when Claude's
is also present, and whether the staged layer needs a root `plugin.json`
(agy's *validator* wants one, static 1, yet *install* succeeded without it,
static 3). So implementation **leads with a read-only probe** on the
installed agy (1.3.4, `~/.local/bin/agy`): read the embedded user guide for
the hooks schema, and install a scratch plugin variant in a scratch `HOME`
to see which files agy stages, transforms, or demands. The generator is
written from what the probe shows, not from assumption.

## Scope

**Probe first (read-only, scratch `HOME`, no production config touched):**

- The hooks-file schema from agy's embedded user guide; the staging behavior
  for a plugin carrying both Claude and agy surfaces; whether a root
  `plugin.json` is needed and, if so, whether its presence changes what
  Claude Code or Codex read (both resolve their manifest at
  `.claude-plugin/plugin.json`; a root file must be inert for them — a test
  pins that the Claude/Codex guard output is byte-identical with the layer
  present).
- **Gemini coexistence** (amendment d): agy stages into
  `~/.gemini/config/plugins/`, the same `.gemini` tree Gemini CLI owns, and
  Gemini CLI is live until DS8. The probe confirms the staged layer is inert
  for Gemini CLI — its hooks come from `settings.json`, not
  `config/plugins/` — with a listing and a settings read, not an
  assumption.
- **The probe's findings are committed evidence** (amendment f): the schema
  as read, the staging listing, the root-`plugin.json` answer, and the
  coexistence check land in this story package (`evidence/`), with a
  re-runnable route script beside them. DS12.TS3's evidence files were not
  committed, which is why this plan re-derives the schema; that is not
  repeated. TS2 and TS3 build on files, not on a session's memory.

**Generator — `ts/src/guards/claudePlugin.ts`:**

- Three new generated files under `plugins/mirror-mind/`, shapes settled by
  the probe: the agy-schema hooks file (valid, with the hook entries' shape
  in place and behavior deferred to TS2/TS3), `mcp_config.json` whose entry is
  **derived from the same builder function the Claude manifest uses** —
  never a hand-written third copy of the locator — with the MCP-entry
  equality extended to every carrier: the manifest, the hook wrappers, and
  the agy file (amendment a); and `rules/AGENTS.md` carrying the Operating
  Instructions, generated from `AGENTS.md` itself. The guard comparing
  committed to generated bytes on every test run **is** the drift mechanism
  for that copy (amendment b): an `AGENTS.md` edit without regeneration
  fails CI until the plugin is rebuilt, the same discipline the skills live
  under — no second sync check is wanted.
- The guard test extends to the new files: committed bytes equal generated
  bytes, the same contract the manifest and skills already have. As the
  negative control (amendment g), the test regenerates the Claude manifest,
  skills, and hook wrappers **with the layer present** and asserts them
  byte-equal to today's: accidental coupling inside the builder fails in
  CI, not in a reviewer's eyes.

**Wiring — `ts/src/runtime/wiring.ts`:**

- A new runtime row: title Antigravity, command `agy`, steps from the probe —
  expected one step, `agy plugin install "<root>/plugins/mirror-mind"` — and
  never more than two (bar 5). If the probe forces a second *action*, it is
  printed as a numbered step, never a parenthetical: anything requiring
  action gets a number (experience lens). `detectRuntimes` finds `agy`;
  `runtimeWiringLines` prints the steps; `ORDER` gains the runtime.
  **No succession language** (amendment e): a machine with both `gemini` and
  `agy` prints both blocks, each just its steps — Gemini CLI is supported
  until DS8, and the replacement sentence belongs to DS8's cutoff.
- `wiring.test.ts`'s honest counts and `initCli.test.ts`'s rendering follow.

**Pack contents:**

- The new files ship under the already-allowed `plugins/mirror-mind/`
  prefix; `REQUIRED_FILES` gains the agy hooks file so a tarball cannot ship
  the skills without the layer. Sequencing (amendment c): this edit lands
  after the probe settles the layer's filenames, in the same change as the
  generator.

**Docs:**

- `docs/getting-started.md`: an Antigravity section with the install steps,
  honest that per-turn injection and logging land with TS2/TS3.
- `docs/product/specs/runtime-interface/index.md`: the wiring table gains
  the Antigravity row; the Codex-style runtime section is deferred to US4,
  when the behavior it would describe exists and is measured.

## Non-Goals

- Do not implement sibling roadmap items: TS2 (session start and per-turn
  injection), TS3 (transcript logging), US4 (the live bar measurement).
- Do not touch Gemini CLI's wiring (DS8's, gated on US4) or Grok's.

  record.
- Do not mutate any production agy config: every probe and route runs in a
  scratch `HOME`.

## Acceptance Behavior

```text
Given the package carries the agy-native layer beside the Claude surfaces
When agy plugin install stages plugins/mirror-mind in a scratch HOME
Then the staged plugin holds all 25 mm skills, the agy-schema hooks file,
  mcp_config.json, and rules/AGENTS.md
And mirror init, finding agy on the PATH, prints the Antigravity steps,
  no more than Gemini CLI's two
And the committed layer files equal the generator's output, and the
  tarball requires the hooks file
And the Claude plugin guard's output for Claude Code and Codex is
  byte-identical with the layer present
```

## Validation Route

Automated:

- `node --test` — the generator/guard cases for the three files, the wiring
  counts and lines, pack contents, and the full suite proving the Claude and
  Codex surfaces unchanged.
- `npx biome check .`

Navigator-visible route:

- Observation 1: in a scratch `HOME` on the installed agy (1.3.4),
  `agy plugin install <pkg>/plugins/mirror-mind`, then list the staged tree —
  pass: 25 `mm` skills plus the three layer files staged; fail: a layer file
  missing, transformed into something agy cannot read, or Claude's hooks
  staged in place of ours.
- Observation 2: `mirror init` on a PATH holding `agy` — pass: the
  Antigravity block prints at most two steps; fail: no block, or more steps
  than Gemini CLI's two.
- Observation 3: `git diff` over `plugins/mirror-mind/` reviewed beside the
  guard test — pass: only additions; the Claude manifest, skills, and hook
  wrappers byte-identical; fail: any Claude/Codex-read file changed.

E2E decision: observation 1 is the E2E — the real agy staging the real
package's plugin in a scratch `HOME`. CI has no agy binary, so the staging
is pinned by generator tests and this live route, the same split DS4's US1
used for Codex.
