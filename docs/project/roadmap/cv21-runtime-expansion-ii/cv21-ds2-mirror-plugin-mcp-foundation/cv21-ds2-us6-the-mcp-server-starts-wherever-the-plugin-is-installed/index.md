# CV21.DS2.US6 — The MCP server starts wherever the plugin is installed

**Status:** 🟢 In Progress
**Type:** User Story
**Delivery Story:** CV21.DS2 — Mirror Plugin & MCP Foundation

---

## User Story

As a person who installed the Mirror plugin on Claude Code, Codex, or Grok,
I want the Mirror MCP server to start in my sessions without any step of my own,
So that the `mirror-mind` tools are there whichever runtime I opened, and however I
opened it.

## Outcome

The plugin's `mcpServers` entry names no `${CLAUDE_PLUGIN_ROOT}`. It starts the server
from a terminal and from a GUI launch whose PATH holds neither the npm bin nor `node`,
on every runtime that takes the plugin as it is. When it cannot start, it says why in
one line on the client's log.

## Acceptance Behavior

```text
Given the plugin installed on Claude Code, Codex, or Grok
When a session starts
Then the mirror-mind server starts, and Claude Code and Codex offer its 7 tools
And the entry in the manifest names no ${CLAUDE_PLUGIN_ROOT}

Given a shell whose PATH holds neither the npm bin nor node, with MIRROR_BIN set
When the entry runs as written
Then the server starts and answers initialize and tools/list

Given no mirror in MIRROR_BIN, on the PATH, or in the global bin directories
When the entry runs
Then it prints one line on stderr naming the install step and exits 1
```

## Scope

- The entry, generated by `buildManifest` and covered by the drift guard.
- `mcp/launch.sh` retired, and its tests moved to the entry.
- The smokes, `retiredSurfaces`, REFERENCE, and the runtime-interface spec.

## Out Of Scope

- Grok attaching the server once started (DS12.TS4 L6): DS10's.
- `runtime diagnose` running the same locator: a follow-up Change Request.

## The Spike

Two candidates were measured before anything was written, on 2026-10-13, with
`bash route.sh entry` from this package, against this tree's package installed in a
scratch prefix, with no model call:

- **A, an inline locator:** `command: /bin/sh`, `args: ["-c", "<locator>"]`. The
  locator runs the search `mcp/launch.sh` runs today: `MIRROR_BIN`, the PATH,
  `~/.nvm/current/bin`, `/opt/homebrew/bin`, `/usr/local/bin`; `MIRROR_NODE` first for
  node, then the directory `mirror` was found in. POSIX `sh`, no `${…}`, no positional
  parameters.
- **B, the bare bin:** `command: mirror`, `args: ["mcp"]`.

| # | Finding | How it was measured | Result |
|---|---------|---------------------|--------|
| 1 | Both start the server from a shell with the npm bin on the PATH | the entry run as written, handshake and `tools/list` | ✓ A and B: `mirror-mind 0.32.1 · 7 tools` |
| 2 | From a GUI-launch PATH (`/usr/bin:/bin`, `MIRROR_BIN` set), A starts and B does not | the entry run as written under that environment | ✓ A: 7 tools. ✗ B: `spawnSync mirror ENOENT` |
| 3 | Claude Code 2.1.296 renders both verbatim and starts both | `claude mcp list` in a scratch `CLAUDE_CONFIG_DIR`, the plugin linked as `@skills-dir` | ✓ `✔ Connected`, the locator shown byte for byte. `claude mcp get` shows Claude Code sets `CLAUDE_PLUGIN_ROOT` and `CLAUDE_PLUGIN_DATA` for the server |
| 4 | Under the GUI-launch PATH, Claude Code connects A and not B | the same, with `env -i PATH=/usr/bin:/bin MIRROR_BIN=…` | ✓ A connects. ✗ B: `Failed to connect — ENOENT: Executable not found in $PATH` |
| 5 | Grok 1.0.52 starts both and completes the handshake | `grok plugin install --trust`, then `grok mcp doctor` in a scratch `HOME`, `MIRROR_HOME` in the environment | ✓ `handshake OK (protocol 2025-11-25)`, `7 tools discovered`, A and B |
| 6 | **Grok substitutes set environment variables by name inside the args at load time.** `"$HOME/.nvm/…"` became the path; unset variables and the script's own stayed as written | the entry as `grok mcp doctor` prints it | A variable of the locator's with a name a person exports would be replaced. The locator's variables are `mmbin`, `mmnode`, `mmdir` |
| 7 | Grok passes `MIRROR_HOME` to the server. Without a configured home, `mirror mcp` exits with a stack trace before the handshake | `grok mcp doctor` with and without `MIRROR_HOME` | ✓ with. Without: `MirrorHomeNotConfiguredError`, as a stack trace, not one line (a discovered issue below) |
| 8 | Codex 0.162.1 renders both verbatim | `codex plugin add` from a local marketplace in a scratch `CODEX_HOME`, then `codex mcp get mirror-mind` | ✓ `command: /bin/sh`, `args: -c <the locator>`, byte for byte. The start is the live session's, the Navigator's |

Binaries: `claude` → `~/.local/share/claude/versions/2.1.296`; `codex` →
`/opt/homebrew/Caskroom/codex/0.162.1/bin/codex`; `grok` →
`~/.grok/downloads/grok-1.0.52-macos-aarch64`. Full outputs: `evidence/` in the route's
scratch directory.

**Decision: A.** It is the only entry that starts from a GUI launch (findings 2 and 4),
it survives every runtime's rendering (3, 6, 8), and it keeps the one-line failure. The
"no mirror anywhere" case is measurable only where no global install sits in a
fallback directory, so its proof is the unit test, on CI.

## Discovered Issues

- `mirror mcp` with no Mirror home configured dies with a Node stack trace on stderr
  (`MirrorHomeNotConfiguredError`), where the launcher's own failures are one line. A
  client's MCP log should get one line here too. Not changed in US6; a Change Request
  candidate.
- Grok's `inspect --json` lists the server under `mcpServers` and reports
  `provides.mcpServers: 0` for the plugin at the same time. Grok's, noted for DS10.

## Validation

`bash route.sh static` measures the shipped entry the way the spike measured the
candidates. The live sessions prove the start inside each runtime (test guide).
