# v0.33.2 — Git Runs Where Mirror Lives

**Date:** 2026-10-15

## Highlights

- **On a clone install, `runtime status`, `version`, and `diagnose` describe the install
  from any directory** (CR138). A healthy clone is `ready` everywhere. The channel row is
  what `runtime channel` reports, and the clone role is the checkout's own.
- **`diagnose` grades Mirror's own tree.** Run inside another project, it reported that
  project's uncommitted files as Mirror drift and advised committing, stashing, or
  discarding them. It no longer looks there.
- **A checkout you did not make can no longer run a command through these commands.**
  Git reads a repository's `.git/config`, where `core.fsmonitor` names a command git runs
  on `status`. Run inside such a checkout, `runtime status`, `version`, and `diagnose` ran
  it. They now run git only in the install's own checkout. `version --start PATH` is the
  one documented way to inspect another repository.
- **Package installs were never exposed.** A package inspects no repository; its
  clone-role row now reads `none (package install)`.
- **An install that cannot be identified inspects no repository**, and says why;
  `update --check` answers `unknown` with the reason.

## Where We Started

`v0.33.1` made the welcome card, the status line, and both release-notes readers answer
for the install instead of the cwd. CR138, captured during that work, named the same
defect in `runtime status` and `runtime version` for a clone: both named the install on
their first line, then reported the repository, git state, and channel of whatever
directory they were run in. REFERENCE.md's recommended update flow begins with `runtime
status`, so a clone user who ran it from a project was told `attention needed` about a
healthy install.

Selection found more than the capture said. The clone-role row read the cwd too.
`runtime diagnose` built the same report, so from inside another project it listed that
project's uncommitted files as Mirror's and recommended discarding work in a repository
that was not Mirror's. The plan's review then measured the third face. Git runs a
repository's own `core.fsmonitor` command on `status`, so these commands, run inside a
checkout someone else made, ran what that checkout chose. No skill runs these commands,
so it took a person running them there. The exposure was clone installs, and installs
that cannot be identified; a package never inspected a repository.

## What Changed

**One rule says where the repository rows come from.** `inspectionRootFor(install,
start)`: `--start` when given, else a clone's own checkout, else nowhere. The report
builder and `runtime version` both use it. The builder no longer defaults to the cwd, and
`status`, `diagnose`, and the update gate pass none.

**The rows are the install's.** The channel row is the answer `runtime channel` gives,
and the clone role is the checkout's marker. `diagnose`'s worktree findings come from the
install's tree, so a dirty Mirror checkout is still reported and another project's work
never is.

**`--start` is the one explicit exception.** `runtime version --start PATH` keeps its
documented meaning, to inspect the repository at PATH, and is now named as the one way
these commands run git in a repository the install does not own.

**An install that cannot be identified asks nothing.** Its git rows say `install kind
unknown: <reason>`, and its verdict is `attention needed`, which is true: `runtime
update` refuses such an install. `update --check` answers `unknown` with the same reason
instead of asking the cwd's git.

The tests run every command from a directory in no repository and from a hostile project:
uncommitted work, its own channel and role markers, and a `core.fsmonitor` that creates a
marker file. The answers are byte-identical, and the marker never appears, except through
`--start`, which asks for it. No golden changed.

### What you will notice

- On a clone, `runtime status` gives the same answer from any directory as from the
  checkout, and `runtime version`'s `Update channel:` matches `runtime channel`.
- On a package, `Clone role: none (package install)`.
- `runtime diagnose` may still report `front_door_errors`. Every command that exits 1 to
  report a verdict, `diagnose` included, is logged as an error and counted. That is
  CR139, captured and not in this release.

## Upgrading

```bash
mirror runtime update          # or: npm install -g mirror-mind
```

There is no database migration, and no runtime wiring changes. The update itself is run
by the version you have now; the fix applies from the first command after it.

## Conscious Exclusions

- **Counting verdicts as front-door errors** (CR139). `runtime status`'s `attention
  needed`, `diagnose`'s findings, and `release-notes pending`'s `unknown` exit 1, and the
  front door logs every non-zero exit as an error that `diagnose` counts. This release
  removes the false verdicts that fed it, not the loop.
- **The `release` environment's ref check** (CR136).
- **Retiring `version --start`.** It was kept, as the explicit override it always was.

## What We Learned

In CR133 to CR135, "never the cwd" was a correctness rule: the person's project is not
Mirror, so it cannot answer Mirror's questions. CR138 showed it is also a trust boundary.
The cwd's repository configures the very git that inspects it, so a wrong answer and an
executed command had the same cause and the same fix, which is where a command decides to
look.

A test can pin a defect as faithfully as it pins a feature. One CLI test asserted, with a
comment saying so: "Git inspection still describes the cwd." It was right about the
oracle and wrong about the product, and it now pins the fix.

## Next Horizon

CR139, the verdict loop, is the visible next step in RS010. CR136 would harden the
publish route.
