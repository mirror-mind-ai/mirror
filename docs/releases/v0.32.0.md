# v0.32.0 — One Language, One Install

**Date:** 2026-10-11

## Highlights

- **Install is one command and no checkout:** `npm install -g mirror-mind`, then
  `mirror init <you>`. Two bins on the `PATH`, `mirror` and `mirror-hook`; configuration in
  `~/.config/mirror/env`; your home at `~/.mirror-minds/<you>`. Node.js 24 or newer is the
  only prerequisite. See [Getting Started](../getting-started.md).
- **No Python anywhere.** `src/memory/`, `uv`, `pyproject.toml`, and every way to reach
  them are gone from the repository, and a guard proves the shipped package holds none by
  path and by content. The TypeScript engine owns the database: bootstrap, migrations, and
  every read and write.
- **Each runtime wires by a counted step:** Pi 1, Claude Code 1, Gemini CLI 2, Codex 2,
  printed by `init` for the runtimes it finds, and the Operating Instructions reach each
  runtime its own way.
- **The same commands, the same answers.** 31 front-door commands, 25 skills in three
  copies that all say `mirror`. The last command family was proven byte-identical to the
  Python oracle before the oracle was deleted.
- **Upgrading from a clone is four lines** and is described below; the previous release's
  updater completes the hop and then reports a failure it cannot help, which this note
  explains.
- **Eleven surfaces are retired with cutoffs rather than ported**, each with what to do
  instead and what still works if you do nothing: the web console, the Windows Frame and
  installer, the Python extension API, journey projections, and seven smaller ones.
  Summarized below; the full record is [Pending Cutoffs](pending-cutoffs.md).
- **One behavior change a Pi user can notice:** a new home imports only the Pi sessions
  that are newer than itself. Your earlier Pi history stays where it is.
- **Not in this release:** Windows, Mirror Desktop, a programmatic API. Each is named
  under Conscious Exclusions.

## Where We Started

Mirror Mind was a Python core with four runtime harnesses written in TypeScript around it.
Installing it meant cloning the repository, running `uv sync`, keeping a `.env` in the
clone, and opening your harness inside that directory, because the directory *was* the
install. Every skill called the core by its path inside the clone. The Windows path was a
separate Electron Frame with a PowerShell installer that cloned the repository for you.

That shape worked for its first users and could not reach the next ones. Two languages
meant two toolchains on every machine and two sets of idioms for every contributor. A
clone is not a thing you can tell a stranger to install. And the harnesses, the MCP
ecosystem, and the plugin formats Mirror lives in are all TypeScript; the core was the
one piece that was not.

On 2026-06-23 the decision was taken to
[port the core to TypeScript through a database-seam strangler, not a rewrite](../project/decisions.md#mirror-mind-ports-to-typescript-via-a-database-seam-strangler-not-a-rewrite):
the shared SQLite database would be the seam, a TypeScript front door would take one
observable command at a time, each proven against the Python engine on copies of real
databases before it answered anyone, and Python would dissolve as the front door grew.
No big bang, no freeze, no feature pause: the Python product kept moving through
v0.31.14, and every change to it created named parity scope on the TypeScript side.

From 2026-09-07 the migration was a
[single-owner effort](../project/decisions.md#cv22-becomes-a-single-owner-migration), with
a multi-persona technical review standing in as the second opinion at each plan and each
handoff. And from 2026-09-13 it was decided that
[CV22 releases once, when the migration is complete](../project/decisions.md#cv22-releases-once-when-the-migration-is-complete):
a half-migrated core is not a product story, so nothing shipped until all of it had.

## What Changed

### The strangler, in ten Delivery Stories

The arc ran from a parity spike on hybrid search (DS1), through a read-only TypeScript
foundation (DS2) and a Pi front door that wrapped the unported remainder (DS3), to
deterministic writes (DS4) and the external-API commands, extraction and embeddings among
them (DS5). DS6 moved schema custody: the TypeScript engine took over database creation
and migrations, and proved a fresh database it creates is structurally identical to one
Python created. DS7 burned down the remaining command surface, fourteen stories, until
the deterministic Python command surface was empty. DS8 cut the live providers over.
DS9 ported the MCP server, with a threat model first and wallet guards against denial of
spend. DS10 retired what was left and made the package.

Every ported family answered from TypeScript behind a one-variable revert to Python while
it was young, and every revert was removed only when Python itself was. The oracle
harness that graded TypeScript against Python on copies of real databases went with the
oracle; its goldens are frozen fixtures the tests still grade against.

### Deletion as a product decision

Not everything was ported. Where a surface had no user the migration could name, it was
[retired with a cutoff rather than carried across](../project/decisions.md#the-web-console-is-retired-not-ported-and-ds7-closes-at-1414):
the web console, whose successor is `mirror-gui`; the
[Windows Frame and installer](../project/decisions.md#the-windows-frame-and-installer-are-retired-not-re-homed-and-no-windows-story-is-promised),
with three downloads ever and no known user; the Python extension API and the
compatibility host that served it;
[journey projections](../project/decisions.md#journey-projections-retire-with-the-python-core-mirror-desktop-is-outside-the-migration),
whose one consumer is outside the migration; the SQLite Refinement Workbench, replaced by
the file-first Refinement route; the legacy database conversion, the migration rehearsal
tool, the journey admin verbs, the metadata backfill, and the Python-era release tooling.
Each cutoff answers what no longer exists, what to do instead, and what still works if
you do nothing. The full record, one section per surface, is
[Pending Cutoffs](pending-cutoffs.md); the short version:

| Removed | Instead |
|---|---|
| The Python core: `python -m memory …`, `uv`, the `MIRROR_TS_*` reverts, the Python API | `mirror <command>`; clean `MIRROR_TS_*` and the three path variables out of `.env` |
| The web console (`python -m memory web`) and its scene synthesis | Everything it showed is in the terminal: `journeys`, `journey <slug>`, `memories`, `conversations`, `tasks`, and the four modes; `mirror-gui` is the graphical successor; the scene synthesis has no replacement |
| The Windows Frame and PowerShell installer | Nothing on Windows in this release; a Frame install keeps working on `v0.31.14` and must not update from inside the Frame |
| `register(api)`, `extension.py`, the compatibility host | An extension declares a runtime per capability in `skill.yaml`; install validates what the manifest declares |
| Journey projections and `.mirror/projections` | Nothing; existing trees are inert; Mirror Desktop stays on the last Python-bearing release |
| The SQLite Refinement Workbench's twenty verbs | `docs/project/refinement/index.md` and the file-first route |
| `migrate-legacy` (the Portuguese-era conversion) | Convert once with the last Python-bearing release; any home Mirror has ever opened is already current |
| `memory-rehearse-migration` | The TypeScript engine's own migration tests; backups before every write |
| `journey export-registry` and `journey mutate` | `journeys` and `journey <slug>` to read; the Mirror, Builder, and Explorer surfaces to change; no machine-readable dump |
| The conversation metadata backfill flags | Nothing: a one-shot pass whose moment has passed; the lifecycle faces stay |
| `runtime release-doctor` and `release-promote` | Maintainer scripts, `npm run release:doctor` and `release:promote`, from a checkout |

The last tree that contains the Python core is kept at the
[`cv22-last-python-bearing`](https://github.com/mirror-mind-ai/mirror/tree/cv22-last-python-bearing)
tag, so nothing is gone from the world, only from this version.

### The package

The repository is the package: `npm pack` produces 468 files with the same paths as a
checkout, two bins on a loader shim that strips types for its own package only, no build
step, no install script. The core reads its configuration in one order — environment,
`<clone>/.env`, `~/.config/mirror/env` — and `init` writes `MIRROR_USER` there, readable by
you only, never taking a key from the command line. All 25 skills, in the Pi, Claude
Code, and plugin copies, say `mirror` under a guard that forbids any other form. A smoke
in CI packs, installs into a scratch prefix, initializes, seeds, opens a migrating
database, exercises the four runtimes' wrappers and the MCP server, and proves no
interpreter was spawned.

The package is published by npm's trusted publisher for this repository:
[staged from CI with provenance, and a maintainer makes it public with 2FA](../project/decisions.md#the-npm-package-is-published-by-staging-from-ci-with-provenance-and-a-maintainer-approves-with-2fa).
No long-lived token exists. The route was rehearsed end to end before this release.

### One behavior change

[A new home imports only the Pi sessions that are newer than itself](../project/decisions.md#a-new-mirror-home-imports-only-the-pi-sessions-that-are-newer-than-itself).
Session maintenance used to backfill every untracked Pi session on the machine; for a
home that had tracked Pi from the start that filled gaps, but for a new home it copied
the person's whole Pi history, from every project, and then spent on retitling and
extracting it before the first prompt was answered. Now a session is Mirror's only if it
ended after the home existed; the home's age is its database's first open. For an
existing home, nothing changes: your home is older than your sessions. The one case where
a person loses an import they used to get: a database rebuilt from scratch is a new home,
born now, and the sessions the old one held are not imported again. The home is the
database.

## Upgrading from a clone

Until this release Mirror ran from a git clone and the skills called the core by its path
inside it. The skills now say `mirror`, and nothing provides that name until you do, once.
Node.js 24 or newer is required, and was not before: check `node --version` first.

```bash
cd <your clone>
git pull            # or: mirror runtime update, from the next time on
npm ci
npm link            # puts `mirror` and `mirror-hook` on your PATH from this tree
mirror runtime status   # should say: Install: clone (<your clone>)
```

Keep opening your harness in the clone, as before; everything it finds there now answers
through `mirror`. Your `.env` stays where it is. Your home and database are untouched; the
first command to open the database applies the pending migrations, backup first.

**If you updated with the previous release's `runtime update`**, it fast-forwards and then
reports that its post-update check failed. It did: that check runs the Python engine, and
the tree it just updated to has none. The update itself completed. Run the lines above,
and from then on `mirror runtime update` is the Node one.

Then the housekeeping the cutoffs ask for: remove any `MIRROR_TS_<FAMILY>=0` line and
`EXPORT_DIR`, `TRANSCRIPT_EXPORT_DIR`, `DB_BACKUP_PATH` from `.env` (`mirror runtime
diagnose` names the stragglers); if your `identity/user/identity.yaml` still says `uv run
python -m memory identity edit`, the command is `mirror identity edit user identity`;
`.venv` and `uv` are dead weight and can go; and if you have extensions with their own
skills, re-run `mirror extensions sync` after their repositories are updated.

**You can move to the package instead** of keeping the clone: `npm install -g
mirror-mind`, `mirror init <your-name>` (it finds your existing home by name and copies
nothing), add your `OPENROUTER_API_KEY` to `~/.config/mirror/env`, run the wiring step
`init` prints for your runtime, and delete the clone. A checkout opened in Pi and an
installed package both provide the extension; there is no reason to keep both.

## Conscious Exclusions

- **Windows.** The Frame and installer are retired and no Windows story is promised. The
  supported platform is POSIX (macOS, Linux). A Frame install keeps working on
  `v0.31.14` as it is, and must not update from inside the Frame.
- **Mirror Desktop.** Outside the migration. It couples to the Python era well beyond
  projections and stays on the last Python-bearing release; its integration with the
  TypeScript core is a separate effort after this one.
- **A programmatic API.** `from memory import MemoryClient` has no TypeScript
  counterpart in this release. The command line and the MCP server are the interfaces.
- **A Gemini extension and Codex hooks.** Both runtimes wire by two documented steps and
  Codex runs through a shipped wrapper; a packaged Gemini extension and Codex hooks were
  considered and not built.
- **Importing earlier Pi history on request.** The new rule does not ask and offers no
  import of what it skips; if one is wanted, it is a feature with its own story.
- **`v1.0.0`.** This release completes a Capability Value, which the versioning rule
  would call a MAJOR, but
  [that number is CV9's](../project/decisions.md#cv22-releases-as-v0320-not-v100): a
  migration built not to be noticed does not get to be the 1.0.

## What We Learned

**The seam was the method.** Choosing the database as the boundary, rather than an API or
a module, meant the two engines could run side by side over the same real data for three and
a half months, and parity could be graded as resulting database state rather than argued. Every
family flipped with a revert and lost it only when the oracle it would revert to was
gone.

**Deletion needs the same rigor as construction.** The surfaces retired here each got an
inventory, a decision with the alternative written down, a cutoff that answers three
questions for a user, and a guard in CI that keeps them retired. A retirement that was
only a deletion would have come back.

**A single owner needs a written second opinion.** With one person on the migration from
September, the multi-persona plan and handoff reviews were not a supplement to review;
they were the review. They found the loader shim Node's type-stripping needed, the
operating instructions that had not shipped, the fail-open default in the backfill rule,
and the full-scan that rule would have introduced.

**The documentation is read by the next session, not the next person.** Resumable
plateaus with handoff statements, decisions recorded near the roadmap, and routes written
so a stranger could run them made a part-time migration survivable across gaps of days.
Where a pointer went stale, work was redone.

## Next Horizon

Mirror Mind is one package in one language, and the roadmap it serves is the product's
again. Mirror Desktop's integration with the TypeScript core is the first thing waiting
on the far side of this release. The Refinement index carries what the migration found
and chose not to fix on its way out, CR124 the last of them, found on this release's own
validation. And CV9, Mirror Mind 1.0, keeps its number.
