# v0.40.0 — A Reply Stays in Its Own Conversation, and a Journey Can Go

**Date:** 2026-11-06

The first stable release under [the release train](../process/versioning.md#the-release-train):
everything merged into `main` since v0.39.5, in one batch. One of its two changes users
have never had; the other reached embedding hosts as a preview on the same day.

## Highlights

- **A session's replies go into its own conversation, and only there**
  ([CR151](../project/refinement/rs010-cv22-oracle-and-port-hygiene/cr151-the-transcript-backfill-writes-a-session-s-replies-into-other-sessions-conversations.md)).
  At `SessionEnd`, on Claude Code and the runtimes that share its hook, the transcript
  filled every conversation in its time window that had no assistant message yet. An open
  conversation that started earlier was always in the window: a session killed in its first
  turn, or a concurrent session still in its own. Now the transcript fills the conversation
  `runtime_sessions` binds to the ending session, inside that conversation's own window.
- **A reply carries its own time.** The copy used to be stamped with the hook's clock, so
  every reply sorted after every prompt of its conversation, and an extraction read all the
  questions and then all the answers. A reply now carries its transcript timestamp,
  normalized to the logger's microsecond form, so recall, extraction, and the MCP read
  model read the turns in order.
- **A transcript nobody owns writes nothing.** A payload with no `session_id`, and a session
  bound to no conversation, used to backfill by window alone. Both are retired: with no
  key there is no attribution. A "same runtime only" fallback was rejected because it would
  not have fixed the recorded case, in which the orphan and the session that wrote into it
  were both `claude_code`.
- **A Journey and its records, deleted in one act**
  ([CR200](../project/refinement/rs010-cv22-oracle-and-port-hygiene/cr200-delete-a-journey-with-its-records-after-showing-what-will-go.md),
  previewed as [v0.40.0-next.1](v0.40.0-next.1.md)). `mirror-mind/desktop` gains
  `previewJourneyDeletion` and `deleteJourneyWithRecords`: the preview counts the Journey's
  records, and the deletion acts only on the preview the person saw, in one transaction,
  behind a named backup verified before any write. Child Journeys refuse.
- No schema change, no migration, and no model or prompt change.

## Where We Started

CV21.DS5.US3's live route on 2026-10-20 found three product defects and stopped at its own
rule: capture, don't fix inside the story. One of them was CR151. A hand-run diagnostic had
left an open `claude_code` conversation with one prompt and no Stop; the route's Claude
session ended at 20:41, and its reply `ready` landed in its own conversation and in the
orphan's, at the same instant. The port had inherited the behavior from the Python fallback
it replaced, written when one session at a time was the only case, and no test pinned the
scoping.

The Navigator accepted the plan after a review through three lenses. The database
architect's finding set the shape: the key already existed (`runtime_sessions.conversation_id`)
and the backfill ignored it, so the fix is to use it, and no fallback survives that the
evidence case would pass through.

## What Changed

**CR151.** `backfillAssistantMessages(db, transcriptPath, conversationId, deps)` takes the
conversation as a required argument: one row, its own `[started_at, ended_at]` window, and
skipped when it already logged a reply, so a Stop-logged one is not recorded twice.
`handleSessionEndHook` reads the bound conversation before `endSession` closes the
session, rather than relying on the close to preserve it. `normalizeTimestamp` pads
Claude's millisecond `.123Z` to the logger's `.123000Z`, because as strings `.123Z` sorts
after `.123456Z`. Both headers say the code departs from the Python port on purpose, so
nobody fixes it back.

The seven-conversation fixture that sat on every window boundary is kept, graded now by
what it was always meant to show: naming one conversation changes it and leaves the other
six exactly as they were. The golden that recorded Python filling all seven at once stays as
a frozen record of the defect, since its generator and its Python source are gone.

**Validated on a real session.** The Navigator ran the route against Claude Code 2.1.318:
the orphan kept its prompt alone, and the session's reply carried the transcript's own
timestamp. Two earlier runs failed, and told us something worth keeping: the Navigator's
machine has Claude settings that pin `MIRROR_BIN` to the installed package over whatever the shell exports,
and a second copy of the plugin loads from `~/.claude/skills`, so both runs executed the
published 0.39.5. They reproduced the defect on a real session (`ready` in the orphan, after
the conversation's close, with no `turn_id`), which is the "before" the CR now records.
The route pins the checkout with `--settings`.

**CR200** is as [v0.40.0-next.1](v0.40.0-next.1.md) describes it: four rules for what
belongs to a Journey, a closed inventory a test holds against the schema, and refusals that
write nothing.

**Also in this release.** The Windows installer's real `MIRROR_NODE` path is named where
docs and comments had named another. The tests and smokes read their paths through
`fileURLToPath`, so a checkout under `Código` or `My Projects` no longer fails 113 tests
(issue #44), and the guard that keeps the product from reading a URL's pathname as a path
now covers them. The lifecycle smoke asserts the new session-less contract. Captured for
later: CR198 (`runtime diagnose` does not name a refused `MIRROR_NODE`), CR199
(`deliverMirrorContext` takes three to seven seconds before a Desktop turn), and CR201.

## Conscious Exclusions

- **Replies already copied stay where they are.** A home that ran an earlier version may
  hold a reply under the wrong conversation. Nothing in the data tells it from a real one,
  and removing one is a manual edit; the selector under Upgrading finds the candidates.
- **A late `SessionEnd` still adds replies after the extraction.** When maintenance closed
  and extracted a conversation first, the replies the backfill then adds are read by no
  extraction. CR151 pins that they land in the right conversation, not what then reads them.
  [CR201](../project/refinement/rs010-cv22-oracle-and-port-hygiene/cr201-a-reply-backfilled-after-the-close-misses-the-extraction-that-closed-the-conversation.md)
  holds the decision.
- **The session-less route is gone, not narrowed.** A caller that fed a transcript alone to
  `conversation-logger session-end` now gets a no-op.
- No CLI command deletes a Journey with its records; a host is the only caller. No cascade
  through child Journeys; files on disk are the host's.

## What We Learned

A fallback written for one case does not know about the second. The Python backfill was
right for a machine with one session at a time, and ordinary use of Mirror, a Ctrl-C in a
first turn, was enough to make it wrong.

The test that proves a fix is the one that runs the code you changed. Two of the Navigator's three live
runs exercised the previous release, because a setting the validator did not know about decided
which Mirror the hooks ran. The checkout's own `mirror-hook` was never in the path. Pinning
the code under test is part of the route now, and the failed runs stay in the record as
the defect, measured on a real session, in the published release.

## Upgrading

```bash
mirror runtime update
```

Update every install that has a home: the fix lives in the core that the hooks run, and a
machine whose Claude Code runs a global install keeps the old backfill until that install
is updated. Plugin copies need no change.

To find replies an earlier version copied into the wrong conversation, read-only:

```bash
sqlite3 ~/.mirror-minds/<user>/memory.db \
  "SELECT substr(a.conversation_id,1,8) AS conv, a.created_at, substr(a.content,1,40)
     FROM messages a JOIN messages b
       ON a.content = b.content
      AND substr(a.created_at,1,19) = substr(b.created_at,1,19)
      AND a.conversation_id < b.conversation_id
    WHERE a.role = 'assistant' AND b.role = 'assistant'
    ORDER BY a.created_at"
```

A match is one reply written into two conversations within the same second, which is the
trace of one backfill; read each row, because two identical short replies a second apart in
different conversations are a different thing. The home's dated backups hold the rows as they
were.
