# v0.31.14 — Change Request Resume

**Date:** 2026-08-30

## Highlights

- Adds `uv run python -m memory build change-request resume --journey <slug> --change-request-id <cr-id>`.
- Restores the active pointer for non-terminal advanced Change Requests without changing their status, evidence, timestamps, RS link, or provenance.
- Lets resumed `implemented` CRs proceed to `validate` and resumed `validated` CRs proceed to `done` through the existing public lifecycle.
- Refuses `captured` CRs with guidance to use `select`, and refuses terminal CRs (`done`, `parked`, `rejected`, `promoted`).
- Documents the command in the runtime reference and Pi Builder skill guidance, with deterministic `REFINEMENT_FLOW_EVENT` rendering for `CR RESUMED`.

## Where We Started

A real Nautilus Harness production Workbench reached a stranded state. RS012 had
CR028 in `implemented`. A sibling CR030 was selected, implemented, validated, and
marked `done`, which correctly cleared the active Change Request pointer. When
the Navigator later validated CR028, `change-request validate` refused with
`Error: active Change Request is required`; trying to reselect it refused with
`Error: cannot select from status 'implemented'; expected captured`.

The Workbench had no public operation to make a non-terminal advanced CR active
again. The only alternatives were wrong: direct SQLite editing, which violates
the public authority boundary, or artificial status regression, which corrupts
the lifecycle record.

## What Changed

`change-request resume` is a narrow recovery primitive. It resolves the requested
CR through the same Journey and active Refinement Story authority guards as the
ordinary CR lifecycle, then updates only the Refinement cursor. The Change
Request row is not rewritten: status, outcome notes, evidence, timestamps,
position, source, provenance, and RS linkage remain intact.

The verb accepts advanced non-terminal states, including `active`, `planned`,
`implemented`, and `validated`. That preserves the one-active-CR invariant while
letting a stranded item return to the correct lifecycle point. A resumed
`implemented` CR can run `change-request validate`; a resumed `validated` CR can
run `change-request done`.

The release intentionally keeps `select` strict. `select` starts a captured CR
and changes its status to `active`; overloading it for recovery would hide the
difference between beginning work and restoring lost focus. `resume` names the
recovery act explicitly.

Ariad surfaces now render `change_request_resumed` as a `REFINEMENT_FLOW_EVENT`
with stage-aware ribbon placement and next-move guidance. Tests cover the
required two-CR reproduction: CR A reaches `implemented`, CR B reaches `done` and
clears the pointer, CR A resumes without row mutation, validates, and completes.
Additional tests prove `validated` resumes to Done and terminal CRs cannot
resume.

## Conscious Exclusions

- No schema migration was added. This is a cursor recovery verb, not a redesign of
  per-CR phase storage.
- The release does not make multiple Change Requests active concurrently.
- Broader revisable lifecycle work in RS003 remains outside this patch: CR010,
  CR012, and CR013 are still captured.
- D-014 remains Carried as a pre-existing runtime-diagnose web-test polling
  budget issue. It reproduced on the parent commit as well as this release
  candidate and is not caused by CR011.
- A one-off process-death lock failure from the complete-suite run was not
  reproduced in isolation on either HEAD or the parent commit; no new debt is
  recorded without further evidence.
- No model pin or prompt changed. The model-behavior `eval --all` release gate is
  therefore not activated.
- Release preparation does not authorize push, PR, merge, tagging, stable
  promotion, GitHub Release publication, or production runtime update.

## What We Learned

A lifecycle that stores active work in one cursor slot needs an explicit recovery
vocabulary. Terminal exits already had public verbs because real refinement work
moves unevenly; resumption deserves the same public boundary. The safe version is
small and explicit: preserve the record, restore the cursor, and let the ordinary
status-driven lifecycle continue.
