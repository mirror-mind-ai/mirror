# v0.36.0 — Five Runtimes, and a Home's Extensions on Every One

**Date:** 2026-10-20

## Highlights

- **Grok Build is the fifth runtime** (CV21.DS10). Two printed steps — a
  trusted plugin install and a home rule for the Operating Instructions — and
  Grok has Mirror's skills, its hooks, and its MCP server. Measured live on
  grok 1.0.62: the rule reaches the model, `/mm-mirror` answers signed by a
  persona, every turn is logged as `grok_build`, the close fits Grok's 1.5 s
  bound. Honest ceiling, written where a user reads it: Grok adds nothing to
  the model's context per turn, so Mirror Mode lasts as long as the skill's
  own instructions do.
- **A home's extensions reach every plugin runtime** (CV21.DS5.US2).
  `mirror extensions install` and `uninstall` regenerate one small plugin per
  Mirror home, `runtime/plugin/mirror-ext-<user>/`, and print the one wiring
  step a runtime on the `PATH` still needs. Chosen over two other shapes by a
  measured table on claude 2.1.296, codex 0.163.0, agy 1.4.2, and grok 1.0.62
  ([decision](../project/decisions.md#user-extensions-reach-every-runtime-as-a-per-home-plugin)).
  `runtime diagnose` names a stale copy and the command that brings it level.
- **An extension's installation settings have a home**
  ([CR145](../project/refinement/rs011-extension-contract-completeness/cr145-an-extension-s-installation-settings-have-nowhere-to-live-but-the-login-shell.md)).
  `~/.mirror-minds/<user>/extensions/<id>.env`, merged *under* the environment
  for the one process Mirror spawns — subcommand or context provider — and
  nothing else. The reason it had to be Mirror: Node reads
  `NODE_EXTRA_CA_CERTS` before any extension code runs, so only the spawner can
  set it, and the alternative was the login shell, where it broke every other
  Postgres client on the machine.
- **Two front-door manners** ([CR148](../project/refinement/rs010-cv22-oracle-and-port-hygiene/cr148-the-front-door-dies-with-a-stack-trace-when-its-stdout-closes-early.md),
  [CR149](../project/refinement/rs010-cv22-oracle-and-port-hygiene/cr149-bind-accepts-a-persona-or-journey-that-does-not-exist.md)).
  `mirror … | head -1` exits 0 in silence instead of dying of `EPIPE` with a
  stack trace — on the hook entry too, where exit 1 was the one code it
  promised never to return. And `mirror ext <id> bind` checks the extension,
  the capability, and the persona or journey before writing a row, refusing
  with the fix in the line: `no persona 'engine' (mirror list personas shows
  this home's)`.

## Where We Started

v0.35.0 closed CV21's runtime set at four — Pi, Claude Code, Codex,
Antigravity — with Grok Build and user extensions named as what remained.
Grok had been reading Mirror's skills by accident since DS12, through its
Claude compatibility, with no hooks and no logging, and DS12.TS4 had left the
MCP attachment as a contradiction: the server ready with its seven tools in
Grok's own view, every session created with `mcp_server_count: 0`. User
extensions reached Claude Code through `expose-claude` and Pi through its
catalog, and nothing else; DS12.TS5 had measured that and left the exposure
as a choice among three shapes, deciding none.

Then the product was used. An extension built for a private journey needed a
TLS mode and a certificate that belonged to the machine, and the only place
the contract left for them was `~/.zshrc`. A mistyped `tail -` produced a
Node stack trace from the front door. A mistyped persona was bound without a
word. Three Change Requests, two days.

## What Changed

**Grok Build, in four stories on one day** (2026-10-18, grok 1.0.62).
CV21.DS10.US1 measured five install shapes and chose two printed steps:
`grok plugin install "<pkg>/plugins/mirror-mind" --trust`, and the Operating
Instructions linked as a rule at `~/.grok/rules/mirror-mind.md` — Grok shows a
session-start hook's context on screen only, so the rule is how the
instructions reach the model. US1 also found that the root `plugin.json`
marker DS7 had added was hiding the plugin's version and MCP server from
Grok; it now carries both, one server on all four plugin runtimes. TS2
closed DS12's contradiction: the server attaches, its tools sit behind Grok's
`search_tool` and `use_tool` meta-tools (as `mirror-mind__list_journeys`), and
the zero count was a snapshot taken while the server was `pending`. US3
measured L3 with an ablation — remove the rule and the model loses the
instructions; the hook canaries never reached it — and the deferred close
tail finished at the next start, DS4.TS2's design on Grok's bound. TS4 wrote
it: the contract's Grok reference implementation, README, Getting Started,
REFERENCE, and the Operating Instructions name Grok Build as the fifth
runtime with its two steps and its ceiling. Paid on the way, CR143: the
inject hook returns at once on Grok instead of spending 2–3 s per load on a
context Grok discards.

**User extensions, chosen then built** (2026-10-19). CV21.DS5.TS1 measured
the three shapes DS12.TS5 had left — user-level skill roots, a per-home
generated plugin, MCP prompts — in scratch homes on all four runtimes, each
cell read by the runtime's own listing and then by one headless turn asking
for a canary, with every tool call classified so a find reached by searching
the disk did not count. Only the per-home plugin qualified on all four: the
skill roots are three roots that no runtime set reads in common, and MCP
prompts attached everywhere and reached no model. US2 built it.
`mirror extensions install`, `uninstall`, and `sync` regenerate
`runtime/plugin/mirror-ext-<user>/` in the canonical plugin's format,
version `0.1.<generation>`, carrying each extension's `claude` skill as its
manifest already declares it — no manifest rewritten. The install prints what
a runtime on the `PATH` still needs: a link for Claude Code, two commands for
Codex, one for Antigravity, one with `--trust` for Grok (and the line that
there is nothing for `--trust` to activate). After a change, the three
runtimes that copy a plugin hold a stale copy until one command each, which
the verbs print and `runtime diagnose` raises as five `ext_plugin_*` findings,
each with its repair. Two homes wire beside each other. `runtime status`
gained `Extensions plugin: mirror-ext-<user> <version> (<n> skills)`.

**The settings file** (CR145). `mirror-cli-v1` handed a subcommand the five
`MIRROR_*` variables and whatever environment `mirror` had; `mirror-context-v1`
handed a provider the environment untouched. Now both read
`extensions/<id>.env` — dotenv, the parser behind Mirror's own `.env` — and
merge it *under* the process environment: an explicit export still wins, the
five `MIRROR_*` names can never come from the file, and the result reaches
that one process. The file sits beside the installed directory, not inside
it: `install` rewrites the directory, and in a development home the directory
is a symlink into the extension's own repository. `mirror ext <id>` ends its
listing with the file's absolute path and one of four states — the variable
*names* it carries, `no variables`, `not present` with what to do, or
`unreadable` with the reason — and says when other users can read it. A file
that exists and cannot be read refuses the subcommand (one line, exit 1,
nothing spawned) and skips the provider with a `settings_unreadable`
diagnostic. A full `uninstall` keeps the file and says so. The contract
reference has the rules in full.

**A closed pipe** (CR148). One listener at each entry — `mirror` and
`mirror-hook` — on `EPIPE`: exit 0, write nothing. `npm`, `cargo`, and
`kubectl`'s choice over git's 141, because under `set -o pipefail` 141 fails a
pipeline a person wrote on purpose. Anything that is not `EPIPE` is rethrown.
The hook leaves one line in `hooks.log` first, `stdout closed early`, because
its try/catch could never see a stream's `error` event, and a runtime that
gives up on a hook closes its pipe. Stop means stop: work after the reader
closes is abandoned, as `SIGPIPE` abandons git's.

**`bind` checks what it binds** (CR149). Four checks before the one insert,
outside in: the id against the manifest's grammar, the extension installed,
the capability declared (the validator first, then the context reader for the
list), the persona or journey present in the identity rows a load is later
matched against. Each refusal is one line on stdout at exit 1 and writes no
row. `unbind` and `bindings` are untouched: removing a row that points at
nothing is the repair. A deliberate divergence from the Python oracle; the
bindings golden kept every byte, with its world given what the checks need.

## Upgrading

```bash
npm install -g mirror-mind@latest    # or: mirror runtime update
```

No migration. Existing homes, sessions, memories, and bindings are untouched.

**Grok Build:** `mirror init` prints the two steps when it finds `grok` on
your `PATH`; Getting Started's Grok Build section has them with what they
cost. If you had wired Claude Code, Grok already read the skills from that
link; after the plugin install each skill appears twice in Grok's menu, and
the hooks run once.

**If you have extensions installed:** the per-home plugin is generated by the
next `extensions` verb, not by the update. Re-install any one extension —
`mirror extensions install <id> --extensions-root <root>` from its source, or
from the home's own `~/.mirror-minds/<user>/extensions` — and the report
prints the one wiring step each runtime on your `PATH` still needs. Pi needs
nothing; its catalog path is unchanged.

**If an extension of yours reads machine settings from your shell profile:**
move them to `~/.mirror-minds/<user>/extensions/<id>.env`, `chmod 600` it,
and `mirror ext <id>` will show the keys it carries. Then delete the exports
— they reached every other program you run.

## Conscious Exclusions

- **DS5 is not closed.** US3 — `review-copy` invoked live on each runtime
  from the shipped package, with version, binary, and date — and TS4 — the
  contract, extension docs, Getting Started, and REFERENCE saying how an
  extension reaches each runtime — remain. Until TS4, the install's printed
  steps and the contract's per-home plugin section are the documentation.
- **DS11**, the contract and docs refresh that folds all five runtimes into
  one parity matrix, is not this release's.
- **An extension cannot yet declare the settings it expects** (CR146), so the
  settings file is written from the extension's README, not from a
  checklist Mirror prints. **`install` shows `suggested_personas` the home does
  not have as if it did** (CR150). **Three copies of the extension-id grammar
  remain, two of them disagreeing** (CR147); CR145 and CR149 used the
  manifest's. All three captured, none done.
- **Still open from earlier:** the plugin smoke's negative probe on a machine
  with a global `mirror-hook` (CR142); the DS7 routes removing agy's credential
  where 1.3.x kept it (CR144).
- **141** as the exit on a closed pipe, and `EPIPE` handling inside extension
  subcommands: not chosen, recorded in CR148.

## What We Learned

Twice in one day a validation route had to be shown failing before it could
be trusted passing. CR145's first run validated nothing: the `mirror` on the
Navigator's `PATH` was the published 0.35.0, and the shell wrapped it in the
very function the CR retires — the workaround, measured where it lived. CR148's
planned control, `| head -1`, could not fail: a 2 KB listing lands whole in
the pipe buffer before `head` quits, so there was never an `EPIPE` to handle;
the reproduction is a reader that closes without reading. A route that names
the binary by path and a control that has been seen red are now part of what
a Change Request's validation means.

The three CRs came from using the product, not from reading it: a private
journey's extension, a typo, another typo. The review that preceded each —
five lenses on CR145, three on CR148, four on CR149 — changed each plan
before a line was written, and the things it added (a result type instead of
a throw, a diagnostic kind instead of a generic failure, a check zero on the
id grammar) are the parts a future reader will be glad of.
