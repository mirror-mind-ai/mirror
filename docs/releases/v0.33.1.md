# v0.33.1 — The Install Answers For Itself

**Date:** 2026-10-15

## Highlights

- **The welcome card and the status line announce the update the running install
  has** (CR135). A package asks the registry for its channel's version, a clone its own
  checkout and remote. Before, both asked the git repository of whatever directory the
  session started in: another project's tag could be announced, a package was never told
  of a release, and the status line kept a stale `⬆` after the update.
- **npm runs in the install's own directory**, for the card and for `runtime update`, so
  a project's `.npmrc` can no longer choose the registry the card reads and the update
  installs from.
- **`release-notes latest` and `vX.Y.Z` read the notes the package ships** (CR133). On a
  Homebrew install on Apple Silicon, where `/opt/homebrew` is itself a git repository,
  they answered `Release notes: not found`.
- **`release-notes pending` answers for the install, never the cwd** (CR134). A clone
  reads its own channel's ref in its own checkout. A package asks the registry which
  version its channel holds and reads that version's notes from its tarball. When
  nothing can answer it says `Pending releases: unknown` with a reason and exits 1, so
  `none` always means a source answered.
- **`--ref` can no longer run a command.** A value like `--upload-pack=<command>`
  reached `git fetch` as an option, and git ran it. Refs beginning with `-` are refused,
  and every git call takes `--end-of-options` before its operands.
- **A clone's update fetch has git's network budget again** (CR132): 120 seconds, not
  the 2 seconds a local git call gets.

## Where We Started

`v0.33.0` was installed onto a Homebrew package on 2026-10-14, and three surfaces
answered wrongly the same day. `mirror runtime release-notes v0.33.0` said `not found`, with
the note sitting in the package. `release-notes pending` said `none` from `/tmp` and,
from inside an unrelated project, listed that project's releases after fetching from its
remote. The welcome card asked the same wrong repository whether Mirror had an update.

The three had one root. The readers were ported faithfully from a Python core that ran
from a checkout, where the cwd, git's top level, and the install were usually one
directory. Under npm distribution they are three: a skill runs in the person's project,
and a global prefix can sit inside someone else's repository. CV22 had already moved the
version and the welcome card's release note onto the running tree, and handed `latest`
that tree. But the reader still climbed out of it to git's top level, and `pending` and
the update check still began at the cwd.

The promotion of `v0.33.0` itself had stumbled on the same day. Its push timed out at two
seconds and was finished by hand (CR132), and npm's `latest` had needed a move nobody's
route printed (CR125).

## What Changed

**Each install asks about itself.** The card, the status line, and `pending` detect the
install from where the front door lives, as `runtime channel` does, with nothing spawned
and no cwd involved. A package reads its channel's dist-tag through the same call `runtime
update --check` makes. A clone runs its check, its tag lookup, and its "commits behind"
count in its own checkout. The channel shown is the install's. On `stable` the card checks
at every render; on `main` it never checks and shows the cached verdict.

**npm's directory is a trust decision.** A four-lens review of CR135's plan found that npm
reads the `.npmrc` of the directory it runs in. A cloned project that ships
`registry=` could therefore choose what the card announced and what `runtime update`
installed. Every npm call the product makes now runs in the install's own root, whose
project config is the package's own.

**One bound for the session start.** The card's remote reads share one 5-second deadline,
and the registry read does not retry, so an unreachable registry costs at most that. A
cached update the install already has is shown by neither surface, and a successful
`runtime update` records `up_to_date`.

**Release notes come from the install.** `latest` and `vX.Y.Z` read `docs/releases` under
the running tree and ask git nothing. `pending` reads, for a clone, `origin/<channel>`
(or `--ref`) in the clone's own repository, after fetching it there. For a package, it
resolves the channel's dist-tag to a version, as `runtime update` does when it plans.
When that version is newer, `npm pack --ignore-scripts` fetches that exact tarball into a
private directory, and its notes are read in memory and the directory removed. When it is
not newer, nothing is downloaded.

Three choices shaped the package path:

- the registry tarball, not the GitHub branch: the branch is a second authority that can
  disagree with the dist-tag, as a half-promoted release does;
- not version numbers alone, which would not answer "what's new in this update?";
- a reader of its own over `node:zlib` rather than a spawned `tar`, which would take
  archive-chosen names as arguments. It stops at 64 MB inflated. It refuses an archive
  that ends before its end-of-archive block, so a cut tarball cannot pass for a whole one
  missing its newest notes.

**`unknown` is said.** A failed fetch, a ref or dist-tag that does not resolve, an
unreachable registry, or an install that cannot be identified answers `Pending releases:
unknown` with a `Reason:` line and exit 1. `--no-fetch` reads a clone's ref as last
fetched; a package keeps no copy of its channel, so it cannot answer offline.

**The ref is an operand.** `--ref` was split at its first slash into a remote and a
branch for `git fetch`, so `--upload-pack=touch X/y`, or `origin/--upload-pack=touch X`,
reached git as an option, and git ran the command. A test claimed this could not happen.
It passed only because its marker path was absolute, which the split cuts at the leading
`/`. The exposure was local: whoever can pass `--ref` can run commands anyway. Refs
beginning with `-` are now refused, and `fetch`, `ls-tree`, and `show` take
`--end-of-options`, which covers the half after the slash.

### What you will notice

- On a package, `release-notes pending` shows `Source: npm mirror-mind@stable (<version>)`.
  On a clone it shows `Source: origin/<channel>`, so a clone on `main` now reads
  `origin/main`, where it used to read `origin/stable`.
- A package on `main` answers `unknown`: npm has no `main` dist-tag, as `runtime update
  --check` already says.
- A `⬆` that the status line kept after an update is no longer shown once the install
  has that version.

## Upgrading

```bash
mirror runtime update          # or: npm install -g mirror-mind
```

There is no database migration, and no runtime wiring changes. The update itself is run
by the version you have now, so this release's changes to it apply from the next update
on: npm running in the install's root, and recording `up_to_date` when it succeeds. A
Homebrew package on Apple Silicon reads its release notes again from the first command
after the update.

## Also In This Release

- **For maintainers.** `release:promote` pushes with the network budget, and a failed push
  shows git's message with a recovery that says what is where (CR132). A `stable` release
  now ends, in both places the route is printed, with `npm dist-tag add
  mirror-mind@<version> latest`. The publish workflow stages under `stable` or `next` and
  nothing else (CR125).
- **For contributors.** The updater smoke gives the same result on any machine, whatever
  the shell exports (CR137). The npm package smoke installs into a prefix that is a git
  repository, the Homebrew shape. Its `npm` is a stub after the install, so it never
  reaches the live registry.

## Conscious Exclusions

- **`runtime status` and `runtime version` on a clone**, which still read the clone's
  repository and channel from the cwd, so a healthy clone reads `attention needed` outside
  its checkout. It is the same family, captured as CR138.
- **The `release` environment's ref check.** It accepts a dispatch from any ref, so a
  branch's own copy of the publish workflow could stage (CR136).
- **A `--channel` option on `pending`**, which `update --check` and `version` have.
- **The `mm-release-notes` skill's wording**, which still says "the current stable
  release", true on the default channel.

## What We Learned

A faithful port inherits its oracle's idea of where it runs. Each of these readers matched
the Python core's goldens, and each was wrong once the program stopped living in the
directory it was asked about. The tests agreed with the oracle for the same reason: they
ran from a clone's root, where the cwd, git, and the install coincide. The new tests for
the card and for `pending` run every case from two places, outside any repository and
inside an unrelated one, and the answer must not move.

A validation route must say which install it tests. On a machine with both a package and
a linked checkout, a bare `mirror` runs whichever comes first on the PATH, and both
report the same version.

## Next Horizon

CR138, the same defect in `runtime status` and `runtime version`, is the visible next
step. CR136 would harden the publish route. RS010's other hygiene requests follow.
